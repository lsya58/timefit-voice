## 0. 現在の状況（まずここを読む）

### 0.1 ひとことで
**MVP の後半。** 販売に必要な機能はそろった。ここからの最優先は「機能の追加」ではなく、**他人の PC で使える品質**と、**お金を払ってもらえるかの確認**。
新しい音声エンジン・翻訳吹き替え・YMM4 連携などは、5人の試用で需要が確認できるまで作らない。

### 0.2 できているもの（v0.4.0）
- 尺合わせ: 等倍 → 句読点の間を詰める → 話速（上限あり）→ AI 要約（1回で3案を出し、収まって情報が一番多い案を自動採用）。サンプル単位で目標の長さに一致
- 入力: SRT / VTT / CSV（Shift_JIS 可）。出力: 行ごとの WAV、まとめ WAV、修正後の字幕、結果一覧、クレジット
- 画面: タイムライン表示、「発話＋無音＝合計」の表示、試聴、ドラッグ＆ドロップ、サンプル字幕ボタン、設定・動作チェック
- **AI 要約の確認画面**: 原文と案を全文で比較（削られた部分を赤で表示）、消えた数字・固有名詞らしき語を警告、案の切り替え・別案の追加・手書き修正、選んだ文で1行だけ作り直し（出力ファイルも自動更新）
- Gemini の混雑・上限への自動リトライと予備モデルへの切り替え
- 無料版（1回10行）/ 製品版の切り替え、exe ビルドスクリプト、購入者向けマニュアル、販売ページ下書き
- 自動テスト 62 件（VOICEVOX と Gemini を偽物に差し替えて WSL 上で実行）

### 0.5 処理速度の調査（2026-11-03、v0.4.1）

**原因**: 遅かったのは Gemini の呼び出し方。VOICEVOX 側ではない。
- 無料枠の `gemini-3.8-flash` は **1日20回まで**（API の応答で確認: `GenerateRequestsPerDayPerProjectPerModel-FreeTier`, 上限 20）。混雑（503）も頻発していた
- v0.4.0 は、上限・混雑のモデルにも「2秒待つ → 4秒待つ → 予備に切り替え」を**要約が必要な行ごと・要約のやり直しごとに毎回**繰り返していた。1日の上限は待っても回復しないので、待ち時間も回数の枠も無駄だった
- 通信のタイムアウトがなく、応答が詰まると待ち続ける可能性があった

**計測**（本物の Gemini ＋ 偽の VOICEVOX、サンプル字幕・要約1行）
| | AI 部分 | 呼び出し |
|---|---|---|
| 修正前（v0.4.0） | 約8秒 | 3.8-flash に3回（すべて上限エラー）→ 予備で成功 |
| 修正後（v0.4.1、旧モデル順） | 約1.2秒 | 3.8-flash に1回（上限と判明）→ すぐ予備で成功。以後 3.8-flash は回復まで使わない |
| 修正後（v0.4.1、新しい既定） | 約1.2秒 | flash-lite に1回 |

モデル別（3案を1回で生成、同じ原稿）
| モデル・設定 | 応答 | 思考トークン | 重要語の保持（6語中） |
|---|---|---|---|
| gemini-flash-lite-latest（既定の思考） | 約1.0秒 | 0 | 4〜6 |
| gemini-flash-lite-latest（thinking: low） | 約0.9秒 | 0 | 4〜5 |
| gemini-3.8-flash | 測定不可 | — | — |

`gemini-3.8-flash` は計測中ずっと混雑・上限で、一度も応答がなかった。品質の比較は回復後に行う。

**修正内容**
1. 1日の上限・混雑・タイムアウトになったモデルは、回復までアプリ全体で使わない（すぐ予備へ）。1日の上限のときは待たない
2. 再試行は1回、待ちは短く（1.5秒、または API が指定する秒数が10秒以内のときだけ待つ）
3. 1回の通信は30秒で打ち切る
4. 既定のモデルを `gemini-flash-lite-latest`（速い・無料枠が多い）にし、`gemini-3.8-flash` を予備にした。思考の深さは `low`（設定で変更可）。旧既定のまま保存されている設定は自動で入れ替える
5. 「数字は算用数字のまま」をプロンプトに追加（「二百六十年」と書かれて「260」が消えた扱いになるのを防ぐ）
6. 工程別の計測: 行ごとに「AI の時間・回数・エラーの種類（503 / 429-day / timeout など）・待ち時間・合成の時間と回数・解析の時間と回数」をログ・report.csv・画面のツールチップに出す。最後に全体の内訳とトークン数を出す（原稿本文と APIキーは記録しない）

**今回やらなかったこと（とその理由）**
- **3案 → 1案への削減**: 3案でも出力は約120トークン、応答は約1秒。1案にしても0.2〜0.3秒ほどしか縮まらない一方、確認画面の比較という強みを失う。3案のまま
- **複数行の並列処理**: 修正後の AI は1行あたり約1秒。VOICEVOX の合成はエンジン側で1件ずつ処理されるため、並列にしても縮むのは AI の待ちだけ。無料枠には1分あたりの回数制限もあり、並列にすると上限エラーが増える。Windows で長い字幕の計測結果を見て、AI の時間が全体の大半を占める場合にだけ、2〜3行の並列を検討する
- **料金の見積もり**: トークン数は記録している（要約1回あたり 入力約290・出力約120）。料金は Google の料金表で換算する。無料枠の範囲なら0円

**Windows で次に確認すること**
- 長めの字幕（20〜50行）を処理し、ログ最後の「処理時間の内訳」を見る。合成が大半なら VOICEVOX 側（CPU 版か GPU 版か）の問題、AI が大半なら並列化を検討する

### 0.5.1 実機での計測結果（full_test.srt、v0.4.1）
| 工程 | 時間 | 割合 |
|---|---|---|
| VOICEVOX の音声合成 | 215.5秒（29回、1行1回） | **約88%** |
| AI 要約（Gemini） | 26.0秒（12回、エラー 0） | 約11% |
| その他（解析・保存） | 数秒 | — |

- **遅さの原因は、開発者 PC の VOICEVOX の合成速度**。話している時間の約1.6倍かかっていた（「えっ！」0.6秒の合成にも3.3秒）。CPU モードと思われる
- アプリ側の無駄はない: 合成は全行1回だけ（見積もりが正確で、作り直しが発生していない）。AI の再試行・待ちも 0
- → 処理時間は利用者の PC と VOICEVOX の設定次第。v0.4.2 で、合成が遅いときに「GPU モード / CPU スレッド数」を案内するようにした
- **AI 要約の品質の問題**: です・ます調の原稿が「来航した」「動き出す」のような常体や、「北斎広重の浮世絵は欧州の画家にも影響」のような見出し調になる行があった。v0.4.2 でプロンプトに口調の指示を追加し、さらに「元の原稿と語尾の調子が同じ案」を優先して採用するようにした

### 0.6 販売時に正確に伝えること
- 合わせるのは**字幕1つ分の区間に、音声全体を収める**こと。単語ごとの発声タイミングを字幕に同期させる機能ではない
- 「ぴったり」モードは、話し終わった後の足りない時間を**無音で埋めて**合計を目標の長さにする（枠いっぱいにゆっくり話すわけではない）

## 1. このシステムが解く課題の整理

### 1.1 価値の本質
「尺が決まっている映像」に「後から音声を付ける」場面で、**書き出し → 長さ確認 → 台本修正 → 再書き出し** の繰り返しをなくすこと。

### 1.2 課題が強く出る場面（＝狙うべきターゲット）
| 場面 | 尺が先に決まる理由 | 課題の強さ |
|---|---|---|
| ショート動画（TikTok / Shorts / Reels） | 60秒などの上限、カットのテンポが先に決まる | 強い |
| 映像が先にある動画（ゲームプレイ、切り抜き、スライド、PV、広告） | 映像を変えずに解説を乗せたい | 強い |
| **字幕から音声を作る／翻訳吹き替え** | 字幕のタイムスタンプが尺そのもの | **とても強い（目標秒数を手入力しなくて済む）** |
| ゆっくり・ずんだもん解説（音声が先） | 尺は音声に合わせて伸び縮みする | 弱い（ここを主ターゲットにすると刺さらない可能性） |

→ **「字幕・映像が先にある」制作フローを主ターゲットにする**のがよい。project_overview.md の「動画1本あたり数十回発生」という仮説は、このターゲットで実際に確認する必要がある。

## 2. PoC 時点の分析（記録）

> 2026-11-03 の PoC（main.py 117行）を分析したもの。ここに挙げた問題は v0.2〜0.3 ですべて対応済み。

### 2.1 できていること
- 等倍生成 → 話速調整（1.3倍まで）→ Gemini で要約 → 再調整、という3段階の流れは一通り動く。
- `.env` で APIキーを管理し、`.gitignore` で除外している。

### 2.2 ドキュメントとのずれ・不具合（優先度順）

| # | 問題 | 内容 | 対応案 |
|---|---|---|---|
| 1 | **「ピッタリ一致」になっていない** | 目標より短い場合はそのまま書き出すので、10秒の枠に6秒の音声が入ることがある。ドキュメントの「1ミリ秒単位でピッタリ」と食い違っている | 足りない分を末尾（または前後）に無音を足して、目標の長さちょうどにする。「以内に収める」「ちょうどにする」をモードとして選べるようにする |
| 2 | **話速調整後に長さを確かめていない** | 話速を上げても、音の長さが倍率どおりに縮むとは限らない（無音部分の扱いなど）。調整後に目標を超えていても成功扱いになる | 生成後に必ず長さを測り、超えていれば倍率を少し上げて再生成（2〜3回まで）。最後は末尾を数ms削るか無音で合わせる |
| 3 | **要約後に1.3倍の上限が守られない** | Gemini の要約が長すぎると、微調整の段階で 1.6倍などの早口になる | 要約後も1.3倍を超えるなら、さらに短く要約し直す（回数に上限を設ける）。最後までダメなら「収まりませんでした」と正直に報告する |
| 4 | **文字数の見積もりが大ざっぱ** | 「1秒7文字」は話者・話速・漢字の割合で大きく変わる | VOICEVOX の `audio_query` の結果に入っている各モーラの長さを足せば、**音声を合成しなくても秒数がわかる**。これで「あと何モーラ減らせばよいか」を計算して Gemini に指示する。合成回数も減って速くなる |
| 5 | **間（ポーズ）を縮める段階がない** | いきなり話速を上げると早口感が出やすい | 「句読点の間を詰める（`pauseLengthScale` 等）→ 話速を上げる → 要約」の順にすると自然に聞こえやすい |
| 6 | **エラー処理がない** | VOICEVOX 未起動、通信タイムアウト、Gemini のレート制限（429）、空の応答などで落ちる | ドキュメントの方針どおり、日本語のわかりやすいメッセージ＋リトライ |
| 7 | **起動時に APIキー必須** | 要約が不要な行しかなくても、キーが無いと起動できない | 要約が必要になった時点でキーを確認する。キー無しでも「話速調整だけモード」で動くようにする（無料版にも使える） |
| 8 | **`temp.wav` を毎回ディスクに書いている** | 一括処理や並行処理で衝突する。不要なファイルが残る | `io.BytesIO` でメモリ上だけで処理する |
| 9 | **Gemini の出力をそのまま使っている** | 「はい、要約しました」などの前置きや、括弧・記号・改行が混ざることがある | 出力形式を指定する（JSON などで本文だけ返させる）、余計な文字を取り除く処理を入れる |
| 10 | **モデル名が固定** | `gemini-3.8-flash` がコードに直接書かれている | 設定ファイルで変えられるようにする（モデルの入れ替わりは早い） |
| 11 | **テストがない** | WSL側からは VOICEVOX に繋がない運用なので、確認が Windows 側の手動実行頼み | VOICEVOX と Gemini をモック（偽物）に差し替えた単体テストを書けば、WSL 上でもロジックを確認できる（ネットワークのブリッジは使わない方針と矛盾しない） |

### 2.3 コード構成の提案
1ファイルのままだと GUI 化のときに困るので、早めに分けておく。

```
timefit/
  engine/voicevox.py   # 音声合成・audio_query・長さ計算
  llm/gemini.py        # 要約（将来ほかのLLMを足せる形に）
  fitter.py            # 尺合わせの判断ロジック（外部通信なし → テストしやすい）
  io/csv_io.py, srt_io.py
  config.py
cli.py                 # Phase 1
gui/                   # Phase 2
tests/
```

## 3. 必要な拡張（製品として売れる形にするため）

### 3.1 入力（目標秒数をどう決めるか）
- **SRT / VTT 字幕ファイル入力【最優先】**: 各字幕の開始〜終了時刻をそのまま目標秒数にする。Premiere / DaVinci Resolve / CapCut / Vrew などで字幕を作っている人がそのまま使える。
- CSV 入力（ドキュメントの計画どおり）: 話者ID・目標秒数・原稿。
- 将来: YMM4（.ymmp）、AviUtl（.exo）のプロジェクトファイルを直接読む。

### 3.2 出力（編集ソフトに戻す手間をなくす）
- 1行ごとの WAV ＋ **字幕のタイミングどおりに並べた1本の WAV**（字幕入力の場合、これをタイムラインに置くだけで終わる）。
- 要約後の文章で作り直した SRT（字幕と音声の内容を一致させるため）。
- **クレジット表記の自動出力**（例: 「VOICEVOX:ずんだもん」）。キャラクターごとに利用規約で表記が求められているので、自動で出せると親切。
- 処理結果レポート（行ごとの「等倍 / 話速◯倍 / 要約あり / 収まらず」）。

### 3.3 品質・使い勝手
- **要約結果の確認・選択画面**: 要約は意味が変わるリスクがあるので、候補を2〜3個出してユーザーが選べるようにする。「この行は要約禁止（話速だけ）」の指定も。
- 話速の上限（1.3倍）、目標との許容誤差をユーザーが設定できるようにする。
- 読み間違い対策: VOICEVOX のユーザー辞書との連携、要約で固有名詞の表記を変えないよう指示。
- 同じ入力の結果を保存しておき、再実行時は Gemini を呼ばない（APIの料金と時間の節約）。
- 目標より大幅に短い場合の改善は、§9.1「長い追加無音を減らす」を参照。販売前は実装を広げず、現行の検知・警告を使用する。

### 3.4 対応エンジンを広げる
- **AivisSpeech、COEIROINK、SHAREVOICE など VOICEVOX 互換の API を持つエンジン**は、接続先のURLとポートを変えるだけで対応できる可能性が高い → 少ない作業で対象ユーザーを増やせる。（各エンジンの互換性は要確認）
- Gemini 以外の LLM 対応は、§9.4「複数AIサービスへの対応」を参照。現行版は Gemini 実装を維持する。

### 3.5 将来の大きな拡張
- **翻訳吹き替え**: 英語字幕 → 日本語に翻訳しつつ尺に合わせて音声化（またはその逆）。翻訳と要約を一度に LLM にやらせられるので相性がよく、海外向けにも売れる。
- 動画編集ソフトのプラグイン化（DaVinci Resolve のスクリプト、Premiere の拡張機能など）。

## 4. 製品化で気をつけること

### 4.1 ライセンス・規約
- **VOICEVOX 本体は同梱しない**（ユーザーに別途インストールしてもらう）。エンジンやキャラクターの規約上、再配布には条件がある。
- キャラクターごとに利用規約（クレジット表記、商用利用の条件、禁止用途）が違う。ツール側では「規約を確認してください」の案内とクレジット出力で支える。
- Gemini の無料枠は、送った内容が Google の改善に使われる場合がある。ユーザーの台本を送ることになるので、販売ページと初回起動時に明記する。

### 4.2 APIキーの壁
非エンジニアにとって「Gemini の APIキーを取ってきて貼る」はかなり高いハードル。

| 方式 | 良い点 | 悪い点 |
|---|---|---|
| **A. ユーザー自身のキーを使う（BYOK）** | 運営側のサーバー・API代が不要。買い切りと相性がよい | 導入でつまずく人が出る → 画像つき手順書・動画が必須 |
| B. 運営側でサーバーを用意し、回数制のクレジットを販売 | キー不要で始められる | サーバー運用・不正利用対策・決済が必要。個人開発には重い |

→ **まずは A**。キー無しでも話速調整だけは使えるようにし、要約が必要な行だけキーを求める。需要が確認できたら B を検討する。

### 4.3 配布
- PyInstaller の exe はウイルス対策ソフトに誤検知されやすい。コード署名証明書（年数万円）を買うか、販売ページに対処方法を書いておく。
- 起動時に「VOICEVOX が起動しているか」「APIキーは正しいか」を診断する画面を作ると、問い合わせが大きく減る。
- 自動アップデート確認（最新版があればお知らせするだけでも十分）。

## 8. Web 版・月額課金の検討（2026-11-03）

### 8.1 結論
**デスクトップ版の検証を止めずに、Web 版は「技術の小さな試作」と「需要の聞き取り」だけ並行して進める。** 本格的な SaaS（認証・決済・利用枠の管理）には、試用者の反応を見るまで投資しない。GPT の二段構えの案に基本的に賛成。そのうえで、実機データから2点を補足する。

### 8.2 実機データから言えること
1. **Web 版の一番の価値は「速さ」かもしれない。** 今回の処理時間の88%は利用者 PC の VOICEVOX 合成だった。クラウドの GPU で合成すれば、2分の字幕が数十秒で終わる可能性がある。「インストール不要」「APIキー不要」に加えて「速い」が売りになる
2. **クラウドの原価はほぼ問題にならない。** 2分16秒の字幕で、合成した音声は約1,000〜1,500モーラ。さくらの単価（1万モーラあたり3円 ※第三者まとめ記事の情報で公式未確認）なら1回0.5円未満。Gemini も要約12回で入力約3,500・出力約1,400トークン程度。**変動費より、決済・サーバー・サポートの固定費と、集客のほうがずっと重い**

### 8.3 Web 版で最初に確かめること（技術の試作）
- さくらの音声合成 API は **VOICEVOX の8キャラクターだけ**。ずんだもん・四国めたんなど、試用者が使っているキャラクターが入っているかが最初の関門（自分の推しキャラがないと使わない人は多い）
- 今のコードは音声エンジンを URL で切り替えられる作りなので、さくらの API が `audio_query` / `synthesis` 互換なら、認証ヘッダーを足すだけで `full_test.srt` を試せる可能性がある。確認すること: 句読点の間（`pauseLengthScale`）が効くか、`audio_query` も課金対象か、30行の処理時間、レート制限
- さくらの規約で、**自分のサービス経由で第三者に音声を作らせること**（再販に近い形）が認められるか

### 8.4 料金の考え方
- 月額600円には反対しないが、**動画を月1〜2本しか作らない人は、使う月だけ契約して解約する**。継続率が低いと、買い切り2,980円より売上が小さくなる
- そこで、月額と並べて**都度購入のクレジット**（例: 60分ぶん 500円、期限なし）を試したい。たまに使う人はクレジット、毎日投稿する人は月額、と選べる形
- 上限は GPT 案のとおり「字幕の合計時間（分）」で決めるのがよい。AI 要約は無料版でも少し体験できるようにする（ここが一番の差別化なので）

### 8.5 需要の確かめ方（追加の開発なしでできる）
§5.3 の5人の試用で、デスクトップ版の感想に加えて次も聞く:
- 「インストール不要・APIキー不要・処理が数倍速い Web 版なら、月額600円 / 60分500円のどちらで、払うか」
- 「今使っているキャラクターは何か」（さくらの8キャラクターに入っているか）
- 「月に何本、何分ぶんの動画を作るか」（必要な利用枠の見積もり）

5人中2人以上が Web 版にお金を払うと答え、かつ使っているキャラクターが提供されている場合に、招待制ベータ（認証あり・決済なし）に進む。

## 9. 将来の改善バックログ（販売後に判断）

> この節は、開発者自身の実利用で得た気付きを失わないための記録であり、販売前の実装予定ではない。現在の優先順位は、販売前品質・安全な exe・実演デモと商品ページ・外部試用・買い切り有料パイロットの順。以下は、外部ユーザーの実作業で必要性が確認された場合にだけ着手する。

### 9.1 長い追加無音をなるべく減らす

- **現在の仕様**: 「ぴったり」は、各行の合成音声が目標より短い場合、末尾に無音を足して行の長さを目標秒数に一致させる。長い追加無音は検知・警告し、`report.csv` で「実発話」「追加無音」「次字幕までの空白」を区別する。「以内」は行別 WAV に末尾無音を足さない。
- **ユーザーが感じた問題**: 15秒枠に約2.87秒の発話を置くと、約12.13秒の機械的な末尾無音になる。秒数は正しくても完成ナレーションとして不自然になり得る。警告は見逃しを防ぐが、無音自体は解消しない。
- **検討する改善方法**: 下限を設けた自然な範囲での話速低下、原稿の加筆候補または字幕時間見直しの提案、意図的な字幕間空白と機械的パディングの見せ分け、ユーザーが明示的に許可した場合だけ行う枠内の音声配置調整。AIによる加筆は意味変更を避け、必ず候補提示と承認を挟む。
- **利点**: 長い無音に気付くだけでなく、映像意図を守りながら自然な完成音声へ近づけられる。
- **既存機能への影響・リスク**: 遅すぎる話速は音質を損なう。加筆は意味・事実・口調を変える危険がある。配置や字幕時刻を自動変更すると映像同期を壊す。設定と確認画面が複雑になる。
- **優先度**: 中（販売前は保留。警告機能で安全性を確保済み）。
- **実装を判断する条件**: 外部試用または有料利用で長い無音が複数の実案件に発生し、警告だけでは作業が完了しない例が2件以上集まること。希望する解決方法と許容できる最低話速も聞き取る。
- **状態**: 保留・未着手。

### 9.2 GUIへの台本直接入力と秒数指定

- **現在の仕様**: SRT / VTT は各字幕の開始〜終了を目標秒数にし、CSV は各行の「秒数」列を目標にする。GUI上で新しい台本を直接作成したり、目標秒数を入力したりする機能はない。
- **ユーザーが感じた問題**: 一般的な読み上げ動画ではメモ帳等で台本を先に書く場合があり、初回利用者には「ぴったり」が何の時間に一致するのか分かりにくい。単発の原稿でも入力ファイルの準備が必要になる。
- **検討する改善方法**: GUIに原稿と「何秒以内／何秒ちょうど」の直接入力欄を設ける。複数行の追加・削除・並べ替え・秒数編集を可能にする。TXTは「本文だけでは目標時間がない」ため、全体秒数の指定、行ごとの記法、または読み込み後の秒数入力を組み合わせて検討する。SRT一括処理は維持し、既存のCSV処理と尺合わせエンジンを再利用する。
- **利点**: CSVやSRTを用意しない利用者も試しやすくなり、単発音声や小規模台本の導入障壁が下がる。
- **既存機能への影響・リスク**: 入力方法が増えると、SRTの絶対時刻、CSVの行枠、直接入力の全体／行秒数が混同されやすい。複数行編集、保存、入力検証によりGUIが複雑になる。TXTの暗黙ルールを作ると誤解を招く。
- **優先度**: 中（需要が確認できれば、販売後の使い勝手改善候補）。
- **実装を判断する条件**: 5人の外部試用で2人以上がファイル準備を主要な障害として挙げる、または直接入力なら継続利用すると回答すること。実際の台本形式と、全体秒数・行別秒数のどちらを使うかを収集する。
- **状態**: 保留・未着手。

### 9.3 生成済みWAVの読み込みと時間調整

- **現在の仕様**: テキストからVOICEVOXで新しい音声を合成して尺を合わせる。既存WAVを入力して伸縮・再配置する機能はない。
- **ユーザーが感じた問題**: 生成済み音声をそのまま時間調整したい場面はあり得るが、現在のテキスト→再合成とは別の処理になる。
- **検討する改善方法**: 音程を保ったタイムストレッチ、許容倍率、音質評価、話者・サンプリング形式の扱いを別技術課題として調査する。既存の字幕／テキスト尺合わせに安易に混ぜない。
- **利点**: 元のイントネーションを調整済みの音声や、VOICEVOX以外の音声も扱える可能性がある。
- **既存機能への影響・リスク**: 音質劣化、外部ライブラリと配布サイズの増加、ライセンス確認、現在の「原稿を短縮して再合成する」設計との分岐が大きい。
- **優先度**: 低。
- **実装を判断する条件**: 有料利用者から具体的なWAV・目標尺・許容音質を伴う要望が複数あり、既存の再合成では解決できないこと。
- **状態**: 別課題として保留・未着手。

### 9.4 複数AIサービスへの対応

- **現在の仕様**: 要約はGeminiを使用する。内部は`Rewriter`を介しており、将来別実装を追加できる構造だが、製品としてサポートするのは現行Gemini経路だけ。
- **ユーザーが感じた問題**: GeminiのAPIキー取得、利用上限、混雑、データ取り扱いが導入障壁になり得る。特定サービスへの恒久的な依存は避けたい。
- **検討する改善方法**: Claude、OpenAI、ローカルLLM等の候補を、3案出力、文字数制約、口調保持、エラー処理、料金、規約の同一評価基準で比較し、プロバイダー選択式にする。
- **利点**: 障害・上限時の選択肢が増え、既に別サービスのAPIキーを持つ利用者にも対応できる。
- **既存機能への影響・リスク**: 設定とサポートが複雑化し、モデルごとの品質差・JSON形式差・料金・規約変更を継続管理する必要がある。選択肢を増やしても非技術者の導入が簡単になるとは限らない。
- **優先度**: 低。
- **実装を判断する条件**: 外部試用・有料パイロットでGeminiが購入または継続利用の明確な障害になり、別サービスなら利用できる人が2人以上いること。候補モデルで既存の品質評価と回帰テストを通せること。
- **状態**: 保留・未着手。現行実装は維持する。
