作成日: 2026-11-03

## 0. 結論（TL;DR）

- **作ろうとしているもの**: 「台本テキスト＋目標秒数」を渡すと、VOICEVOX音声をその尺に収めて返すツール。話速の調整で足りなければ Gemini が台本を要約する。
- **今の段階**: **PoC（1文だけ動く試作）**。117行の `main.py` 1ファイルで、CSV一括処理・エラー処理・GUI・exe化はまだ無い。ドキュメント上は「Phase 1 着手」だが、コードは Phase 0 の最後あたり。
- **一番のリスクは技術ではなく需要**。「音声を映像の尺に合わせる」作業がどのくらいのクリエイターに、どのくらいの頻度で発生しているかがまだ確認できていない。多くの解説動画（ゆっくり・ずんだもん系）は「音声を先に作り、映像を音声に合わせる」流れで作られているため、ターゲットを絞り込む必要がある。
- **次にやるべきこと（優先順）**:
  1. コアロジックの正確さを直す（今は「ピッタリ一致」にも「必ず収まる」にもなっていない）
  2. **SRT（字幕ファイル）入力**に対応する ← 目標秒数が自動で決まるので、CSVより強い入口になる
  3. デモ動画と無料版で需要を確かめる
  4. GUI＋exe化して BOOTH で販売する

## 1. このシステムが解く課題の整理

### 1.1 価値の本質
「尺が決まっている映像」に「後から音声を付ける」場面で、**書き出し → 長さ確認 → 台本修正 → 再書き出し** の繰り返しをなくすこと。

### 1.2 課題が強く出る場面（＝狙うべきターゲット）
| 場面 | 尺が先に決まる理由 | 課題の強さ |
|---|---|---|
| ショート動画（TikTok / Shorts / Reels） | 60秒などの上限、カットのテンポが先に決まる | 強い |
| 映像が先にある動画（ゲームプレイ、切り抜き、スライド、PV、広告） | 映像を変えずに解説を乗せたい | 強い |
| **字幕から音声を作る／翻訳吹き替え** | 字幕のタイムスタンプが尺そのもの | **とても強い（目標秒数を手入力しなくて済む）** |
| ゆっくり・ずんだもん解説（音声が先） | 尺は音声に合わせて伸び縮みする | 弱い（ここを主ターゲットにすると刺さらない可能性） |

→ **「字幕・映像が先にある」制作フローを主ターゲットにする**のがよい。project_overview.md の「動画1本あたり数十回発生」という仮説は、このターゲットで実際に確認する必要がある。

## 2. 現在の実装の評価

### 2.1 できていること
- 等倍生成 → 話速調整（1.3倍まで）→ Gemini で要約 → 再調整、という3段階の流れは一通り動く。
- `.env` で APIキーを管理し、`.gitignore` で除外している。

### 2.2 ドキュメントとのずれ・不具合（優先度順）

| # | 問題 | 内容 | 対応案 |
|---|---|---|---|
| 1 | **「ピッタリ一致」になっていない** | 目標より短い場合はそのまま書き出すので、10秒の枠に6秒の音声が入ることがある。ドキュメントの「1ミリ秒単位でピッタリ」と食い違っている | 足りない分を末尾（または前後）に無音を足して、目標の長さちょうどにする。「以内に収める」「ちょうどにする」をモードとして選べるようにする |
| 2 | **話速調整後に長さを確かめていない** | 話速を上げても、音の長さが倍率どおりに縮むとは限らない（無音部分の扱いなど）。調整後に目標を超えていても成功扱いになる | 生成後に必ず長さを測り、超えていれば倍率を少し上げて再生成（2〜3回まで）。最後は末尾を数ms削るか無音で合わせる |
| 3 | **要約後に1.3倍の上限が守られない** | Gemini の要約が長すぎると、微調整の段階で 1.6倍などの早口になる | 要約後も1.3倍を超えるなら、さらに短く要約し直す（回数に上限を設ける）。最後までダメなら「収まりませんでした」と正直に報告する |
| 4 | **文字数の見積もりが大ざっぱ** | 「1秒7文字」は話者・話速・漢字の割合で大きく変わる | VOICEVOX の `audio_query` の結果に入っている各モーラの長さを足せば、**音声を合成しなくても秒数がわかる**。これで「あと何モーラ減らせばよいか」を計算して Gemini に指示する。合成回数も減って速くなる |
| 5 | **間（ポーズ）を縮める段階がない** | いきなり話速を上げると早口感が出やすい | 「句読点の間を詰める（`pauseLengthScale` 等）→ 話速を上げる → 要約」の順にすると自然に聞こえやすい |
| 6 | **エラー処理がない** | VOICEVOX 未起動、通信タイムアウト、Gemini のレート制限（429）、空の応答などで落ちる | ドキュメントの方針どおり、日本語のわかりやすいメッセージ＋リトライ |
| 7 | **起動時に APIキー必須** | 要約が不要な行しかなくても、キーが無いと起動できない | 要約が必要になった時点でキーを確認する。キー無しでも「話速調整だけモード」で動くようにする（無料版にも使える） |
| 8 | **`temp.wav` を毎回ディスクに書いている** | 一括処理や並行処理で衝突する。不要なファイルが残る | `io.BytesIO` でメモリ上だけで処理する |
| 9 | **Gemini の出力をそのまま使っている** | 「はい、要約しました」などの前置きや、括弧・記号・改行が混ざることがある | 出力形式を指定する（JSON などで本文だけ返させる）、余計な文字を取り除く処理を入れる |
| 10 | **モデル名が固定** | `gemini-3.8-flash` がコードに直接書かれている | 設定ファイルで変えられるようにする（モデルの入れ替わりは早い） |
| 11 | **テストがない** | WSL側からは VOICEVOX に繋がない運用なので、確認が Windows 側の手動実行頼み | VOICEVOX と Gemini をモック（偽物）に差し替えた単体テストを書けば、WSL 上でもロジックを確認できる（ネットワークのブリッジは使わない方針と矛盾しない） |

### 2.3 コード構成の提案
1ファイルのままだと GUI 化のときに困るので、早めに分けておく。

```
timefit/
  engine/voicevox.py   # 音声合成・audio_query・長さ計算
  llm/gemini.py        # 要約（将来ほかのLLMを足せる形に）
  fitter.py            # 尺合わせの判断ロジック（外部通信なし → テストしやすい）
  io/csv_io.py, srt_io.py
  config.py
cli.py                 # Phase 1
gui/                   # Phase 2
tests/
```

## 3. 必要な拡張（製品として売れる形にするため）

### 3.1 入力（目標秒数をどう決めるか）
- **SRT / VTT 字幕ファイル入力【最優先】**: 各字幕の開始〜終了時刻をそのまま目標秒数にする。Premiere / DaVinci Resolve / CapCut / Vrew などで字幕を作っている人がそのまま使える。
- CSV 入力（ドキュメントの計画どおり）: 話者ID・目標秒数・原稿。
- 将来: YMM4（.ymmp）、AviUtl（.exo）のプロジェクトファイルを直接読む。

### 3.2 出力（編集ソフトに戻す手間をなくす）
- 1行ごとの WAV ＋ **字幕のタイミングどおりに並べた1本の WAV**（字幕入力の場合、これをタイムラインに置くだけで終わる）。
- 要約後の文章で作り直した SRT（字幕と音声の内容を一致させるため）。
- **クレジット表記の自動出力**（例: 「VOICEVOX:ずんだもん」）。キャラクターごとに利用規約で表記が求められているので、自動で出せると親切。
- 処理結果レポート（行ごとの「等倍 / 話速◯倍 / 要約あり / 収まらず」）。

### 3.3 品質・使い勝手
- **要約結果の確認・選択画面**: 要約は意味が変わるリスクがあるので、候補を2〜3個出してユーザーが選べるようにする。「この行は要約禁止（話速だけ）」の指定も。
- 話速の上限（1.3倍）、目標との許容誤差をユーザーが設定できるようにする。
- 読み間違い対策: VOICEVOX のユーザー辞書との連携、要約で固有名詞の表記を変えないよう指示。
- 同じ入力の結果を保存しておき、再実行時は Gemini を呼ばない（APIの料金と時間の節約）。
- 目標より大幅に短いとき: 無音で埋めるか、少しゆっくり話させるか、選べるようにする。

### 3.4 対応エンジンを広げる
- **AivisSpeech、COEIROINK、SHAREVOICE など VOICEVOX 互換の API を持つエンジン**は、接続先のURLとポートを変えるだけで対応できる可能性が高い → 少ない作業で対象ユーザーを増やせる。（各エンジンの互換性は要確認）
- LLM は Gemini 以外（Claude、OpenAI、ローカルLLM）も選べるようにしておくと、APIキーを持っていない人の受け皿になる。

### 3.5 将来の大きな拡張
- **翻訳吹き替え**: 英語字幕 → 日本語に翻訳しつつ尺に合わせて音声化（またはその逆）。翻訳と要約を一度に LLM にやらせられるので相性がよく、海外向けにも売れる。
- 動画編集ソフトのプラグイン化（DaVinci Resolve のスクリプト、Premiere の拡張機能など）。

## 4. 製品化で気をつけること

### 4.1 ライセンス・規約
- **VOICEVOX 本体は同梱しない**（ユーザーに別途インストールしてもらう）。エンジンやキャラクターの規約上、再配布には条件がある。
- キャラクターごとに利用規約（クレジット表記、商用利用の条件、禁止用途）が違う。ツール側では「規約を確認してください」の案内とクレジット出力で支える。
- Gemini の無料枠は、送った内容が Google の改善に使われる場合がある。ユーザーの台本を送ることになるので、販売ページと初回起動時に明記する。

### 4.2 APIキーの壁
非エンジニアにとって「Gemini の APIキーを取ってきて貼る」はかなり高いハードル。

| 方式 | 良い点 | 悪い点 |
|---|---|---|
| **A. ユーザー自身のキーを使う（BYOK）** | 運営側のサーバー・API代が不要。買い切りと相性がよい | 導入でつまずく人が出る → 画像つき手順書・動画が必須 |
| B. 運営側でサーバーを用意し、回数制のクレジットを販売 | キー不要で始められる | サーバー運用・不正利用対策・決済が必要。個人開発には重い |

→ **まずは A**。キー無しでも話速調整だけは使えるようにし、要約が必要な行だけキーを求める。需要が確認できたら B を検討する。

### 4.3 配布
- PyInstaller の exe はウイルス対策ソフトに誤検知されやすい。コード署名証明書（年数万円）を買うか、販売ページに対処方法を書いておく。
- 起動時に「VOICEVOX が起動しているか」「APIキーは正しいか」を診断する画面を作ると、問い合わせが大きく減る。
- 自動アップデート確認（最新版があればお知らせするだけでも十分）。

- 買い切りでもメジャーアップデート時に有料アップグレードを用意すれば、継続的な収入になる。

### 5.2 集客
- **このツール自体で作ったショート動画**を X / YouTube Shorts / TikTok に出す（ビフォーアフター: 手作業で何回やり直したか vs. ツールで一発）。
- VOICEVOX 系の Discord やクリエイターコミュニティで、無料版を使ったフィードバックを集める。
- 「VOICEVOX 尺合わせ」「字幕 音声 自動」などで検索に引っかかる解説記事（note / Zenn）。

### 5.3 需要確認のやり方（開発と並行して早めに）
- ターゲット（ショート動画・映像が先にある動画を作る人）5〜10人に、尺合わせにかかっている時間を聞く。
- デモ動画を出して、反応（いいね・「欲しい」コメント・無料版のダウンロード数）を測る。
- 「2,980円なら買う」と言った人の数を数える。反応が薄ければ、ターゲットか機能（例: 翻訳吹き替えに寄せる）を見直す。

### 5.4 競合と差別化
- 競合になりうるもの: 編集ソフトの速度変更機能（音質・自然さで劣る）、海外のAI吹き替えサービス（月額制・日本語キャラ音声に弱い）、手作業。
- アルゴリズム自体は真似しやすいので、**差別化は「日本のクリエイターの道具（VOICEVOX系エンジン・YMM4・AviUtl・字幕ソフト）との連携の良さ」と「非エンジニアでも迷わない使い勝手」**に置く。

## 7. 成功の目安（測るもの）
